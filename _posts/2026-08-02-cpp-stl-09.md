**동시성(concurrency)과 병렬성(parallelism)** 은 코드를 별도의 실행 스레드에서 동작시키는 능력이다.

- **동시성** — 스레드를 백그라운드에서 실행시키는 능력.
- **병렬성** — 스레드를 별도의 코어에서 동시에 실행시키는 능력.

새로운 스레드가 시작되면 기존 스레드에 의해 **부화(spawn)된다**고 표현하고, 스레드 그룹은 **스웜(swarm)** 이라고 부른다.

> 둘의 차이를 한 문장으로 정리하면 이렇다.
> **동시성은 "여러 일을 번갈아 진행하는 구조"** 이고, **병렬성은 "여러 일을 물리적으로 같은 순간에 처리하는 것"** 이다.
> 코어가 하나뿐인 기계에서도 동시성은 성립한다(운영체제가 시간을 쪼개 번갈아 실행한다). 하지만 병렬성은 코어가 여러 개여야 성립한다.
> 그래서 동시성은 **설계**의 문제, 병렬성은 **하드웨어**의 문제에 가깝다.

## 특정 시간 동안 슬립하기

`<thread>` 헤더는 `sleep_for()`, `sleep_until()`을 제공한다.

### How to do it

```cpp
int main() {
    auto t1 = steady_clock::now();
    cout << "sleep for 1.3 seconds\n";
    sleep_for(1s + 300ms);

    cout << "sleep for 2 seconds\n";
    sleep_until(steady_clock::now() + 2s);

    duration<double> dur1 = steady_clock::now() - t1;
    cout << format("total duration: {:.5}s\n", dur1.count());
}
```

두 함수 모두 `std::this_thread` 네임스페이스에 있다. `1s`, `300ms` 같은 리터럴은 `std::chrono_literals`를 열어야 쓸 수 있다.

```cpp
using namespace std::chrono_literals;
namespace this_thread = std::this_thread;
```

### How it works

`sleep_for()`, `sleep_until()`은 `duration` 또는 `time_point`에 도달할 때까지 현재 스레드의 실행을 중단한다.

| 함수 | 인자 | 의미 |
| --- | --- | --- |
| `sleep_for(dur)` | `duration` | "지금부터 이만큼" 잔다 |
| `sleep_until(tp)` | `time_point` | "그 시각까지" 잔다 |

> **왜 둘 다 필요한가?**
> `sleep_for`는 상대 시간, `sleep_until`은 절대 시간이다.
> 일정한 주기로 반복하는 루프라면 `sleep_until`이 유리하다. `sleep_for`는 매 회차마다 처리 시간이 누적돼 주기가 조금씩 밀리지만,
> `sleep_until(next += 100ms)` 방식은 목표 시각 자체를 갱신하므로 **드리프트가 쌓이지 않는다.**

또 하나 알아둘 점은, 두 함수 모두 **"최소한 그만큼"만 보장한다**는 것이다.
스케줄러 사정에 따라 요청한 시간보다 더 오래 잘 수 있다. 실시간 정밀도를 기대해서는 안 된다.

### There's more

일부 시스템은 POSIX 함수인 `sleep()`을 지원한다. 하지만 `sleep()`은 초 단위이고 플랫폼 의존적이므로,
이식성과 정밀도 면에서 `<thread>`의 `sleep_for()`를 쓰는 편이 낫다.

## 동시성을 위해 std::thread 사용하기

**스레드는 동시성의 단위**다.
메인 스레드는 다른 프로세스가 소유한 다른 스레드들과 동시에 실행된다.
`std::thread` 클래스는 STL에서 동시성의 기반이 되는 요소다.

### How to do it

```cpp
void fthread(const int n) {
    cout << format("This is t{}\n", n);

    for (size_t i{}; i < 5; ++i) {
        sleepms(100 * n);
        cout << format("t{}: {}\n", n, i + 1);
    }
    cout << format("Finishing t{}\n", n);
}
```

`main`에서 `std::thread`를 사용하여 별도의 스레드를 실행하면 오류가 생긴다.

```cpp
int main() {
    thread t1(fthread, 1);
    cout << "end of main()\n";
}
```

문제는 `thread` 객체가 범위를 벗어났을 때 무엇을 해야 할지 모른다는 것이다. 그래서 이렇게 해야 한다.

```cpp
int main() {
    thread t1(fthread, 1);
    t1.join();
    cout << "end of main()\n";
}
```

> **정확히 무슨 일이 일어나는가?**
> `thread`의 소멸자는 스레드가 아직 **결합 가능(joinable)** 한 상태면 `std::terminate()`를 호출해 프로그램을 통째로 죽인다.
> 이건 버그가 아니라 **의도된 설계**다. 소멸자가 알아서 `join()`을 하면 예상치 못한 곳에서 멈추고, 알아서 `detach()`를 하면 이미 파괴된 지역 변수를 참조하는 스레드가 남는다.
> 둘 다 조용히 위험하므로, 표준은 "프로그래머가 명시적으로 결정하라"는 쪽을 택했다.

선택지는 둘이다.

```cpp
t1.join();     // 스레드가 끝날 때까지 여기서 기다린다
t1.detach();   // 소유권을 놓는다 — 스레드는 배경에서 계속 돈다
```

`detach()`를 쓰면 `main`이 먼저 끝날 수 있고, 그러면 그 스레드가 참조하던 것들이 사라진 뒤 접근하는 사고가 난다.
특별한 이유가 없다면 **`join()`이 기본**이다.

### How it works

`std::thread`는 스레드의 실행을 의미한다. 객체와 스레드는 **1대1 관계**에 있다.
`thread` 객체는 복사되거나 할당될 수 없으나 **이동은 가능하다.**

```cpp
thread t1(fthread, 1);
thread t2 = t1;              // 컴파일 에러 — 복사 불가
thread t3 = std::move(t1);   // OK — 소유권 이전, t1은 빈 상태가 된다
```

이유는 `unique_ptr`과 같다. 하나의 실행 스레드를 두 객체가 동시에 소유하면 누가 `join()`할지 결정할 수 없다.

스레드를 여러 개 만들 때는 컨테이너에 담아 한 번에 결합한다.

```cpp
vector<thread> swarm;
for (int i{ 1 }; i <= 3; ++i) swarm.emplace_back(fthread, i);
for (auto& t : swarm) t.join();
```

> `emplace_back(fthread, i)`처럼 인자를 넘기면 **값이 복사되어** 스레드로 전달된다.
> 참조로 넘기고 싶다면 `std::ref(x)`로 감싸야 한다. 이건 의도적인 설계로, 실수로 지역 변수의 참조를 넘겨 댕글링을 만드는 걸 막는다.

### There's more

C++20은 `std::jthread` 클래스를 제공하며, 이는 범위가 끝날 때 호출자와 **자동으로 합류(join)** 한다.

```cpp
int main() {
    std::jthread t1(fthread, 1);
    cout << "end of main()\n";
}   // 여기서 t1이 알아서 join된다
```

`jthread`의 `j`는 joining이다. RAII를 스레드에 적용한 것으로, `unique_ptr`이 `delete`를 자동화한 것과 같은 발상이다.

거기에 더해 `jthread`는 **협조적 취소(stop_token)** 를 지원한다.

```cpp
void worker(std::stop_token st) {
    while (!st.stop_requested()) {
        // 일한다
    }
}

int main() {
    std::jthread t{ worker };
    // ... 
    t.request_stop();   // 소멸자에서도 자동으로 호출된다
}
```

첫 인자가 `stop_token`이면 `jthread`가 알아서 넘겨준다.
스레드를 강제로 죽이는 API는 표준에 없으므로, 중단이 필요하면 이렇게 **스레드가 스스로 확인하고 빠져나오는** 구조로 짜야 한다.

## 동시성을 위해 std::async 사용하기

`std::async()`는 대상 함수를 비동기적으로 실행하고, 그 반환값을 전달하는 `std::future` 객체를 반환한다.

### How to do it

`std::async` 함수는 `std::thread`처럼 작업을 실행하지만 `join()`이나 `detach()`를 필요로 하지 않고,
`std::future` 객체를 통해 **반환 값을 받을 수 있다.**

```cpp
prime_time count_primes(const uint64_t& max) {
    prime_time ret{};
    constexpr auto isprime = [](const uint64_t& n) {
        for (uint64_t i{ 2 }; i < n / 2; ++i) {
            if (n % i == 0) return false;
        }
        return true;
    };
    uint64_t start{ 2 };
    uint64_t end{ max };
    auto t1 = steady_clock::now();
    for (uint64_t i{ start }; i <= end; ++i) {
        if (isprime(i)) ++ret.count;
    }
    ret.dur = steady_clock::now() - t1;
    return ret;
}

int main() {
    constexpr uint64_t MAX_PRIME{ 0x1FFFF };
    constexpr size_t num_threads{ 15 };
    list<std::future<prime_time>> swarm;

    cout << "start parallel primes\n";
    auto t1{ steady_clock::now() };
    for (size_t i{}; i < num_threads; ++i) {
        swarm.emplace_back(async(launch::async, count_primes, MAX_PRIME));
    }

    for (auto& f : swarm) {
        static size_t i{};
        auto pt = f.get();
        cout << format("primes({:02}): {} {:.5}\n", ++i, pt.count, pt.dur);
    }

    secs dur_total{ steady_clock::now() - t1 };
    cout << format("total duration: {:.5}s\n", dur_total.count());
}
```

`count_primes`는 백그라운드에서 실행된다.
15개를 순차 실행했다면 전체 시간이 개별 시간의 15배가 되어야 하지만, 실제로는 **개별 시간과 큰 차이가 없다.**
이게 병렬 실행의 효과다.

> **`isprime`의 조건은 사실 틀렸다.**
> `i < n / 2`이므로 `n = 4`일 때 `i < 2`가 되어 루프가 한 번도 돌지 않고 `true`를 반환한다. **4를 소수로 센다.**
> 올바르게는 `i <= n / 2`, 더 나아가 `i * i <= n`이어야 한다(그러면 `O(√n)`으로 훨씬 빨라진다).
> 다만 이 예제의 목적은 "무거운 계산을 백그라운드로 보내는 것"이므로, 느리고 살짝 틀린 것이 **부하 생성용으로는 오히려 편리하다.**

### How it works

`std::async`를 이해하는 데 핵심은 **`std::promise`와 `std::future`** 클래스다.

- **`promise`** — 값을 **넣는 쪽**(생산자 스레드)의 손잡이.
- **`future`** — 값을 **꺼내는 쪽**(소비자 스레드)의 손잡이.

`promise` 클래스는 스레드를 비동기적으로 실행하고 `future` 객체로 그 결과를 나중에 얻을 수 있도록 한다.
`async` 함수는 단순히 `promise`와 `future` 객체 생성을 단순화하는 **헬퍼 함수**다.

```cpp
auto f = async(launch::async, count_primes, MAX_PRIME);
// ... 그동안 다른 일을 한다 ...
auto result = f.get();   // 아직 안 끝났으면 여기서 기다린다
```

`get()`은 **한 번만** 호출할 수 있다. 결과를 이동시켜 꺼내오기 때문이다.
값을 아직 꺼내고 싶지 않고 완료 여부만 알고 싶다면 `wait_for()`를 쓴다.

```cpp
if (f.wait_for(0s) == std::future_status::ready) { /* 준비됨 */ }
```

**실행 정책**을 반드시 짚고 넘어가야 한다.

| 정책 | 의미 |
| --- | --- |
| `launch::async` | 즉시 **별도 스레드에서** 실행 |
| `launch::deferred` | `get()`을 호출할 때 **호출자 스레드에서** 실행(지연 평가) |
| 생략(기본값) | `async \| deferred` — **구현이 알아서 고른다** |

> **정책을 생략하면 병렬 실행이 보장되지 않는다.**
> 기본값에서는 구현체가 `deferred`를 고를 수 있고, 그러면 `get()`을 부를 때까지 아무 일도 일어나지 않는다.
> 위 예제가 `launch::async`를 명시한 이유가 이것이다. **병렬성이 목적이라면 항상 명시하라.**

한 가지 함정이 더 있다. `std::async`가 반환한 `future`의 소멸자는 **작업이 끝날 때까지 블록한다.**

```cpp
async(launch::async, heavy_task);   // 반환값을 안 받으면 여기서 그대로 기다린다
```

임시 `future`가 그 줄에서 바로 파괴되므로 결국 동기 실행이 된다.
그래서 위 예제처럼 `list<future<...>>`에 **담아두는 것이 중요하다.**

## 실행 정책에 따라 STL 알고리즘 병렬로 실행하기

C++17부터 많은 표준 STL 알고리즘은 **병렬 실행**으로 동작할 수 있다.
알고리즘의 작업을 하위 작업으로 분할하여 다수의 코어에서 동시에 실행하는 것을 허용한다.
이 기능은 **하드웨어 지원이 필요하다.**

### How to do it

`std::transform` 같은 함수의 **첫 번째 인수**로 실행 정책을 지정할 수 있다.

```cpp
#include <execution>

std::transform(std::execution::par, v.begin(), v.end(), v.begin(), f);
std::sort(std::execution::par_unseq, v.begin(), v.end());
```

| 정책 | 의미 |
| --- | --- |
| `execution::seq` | 병렬로 실행되지 않음 |
| `execution::par` | 병렬 실행 |
| `execution::par_unseq` | 작업 부하를 **비순차적으로** 병렬 실행 |

C++20에는 `execution::unseq`(벡터화만, 스레드 없음)가 추가됐다.

> **`par`와 `par_unseq`의 차이**
> `par`는 각 요소가 어떤 스레드에서 **처음부터 끝까지** 처리된다고 보장한다.
> `par_unseq`는 그 보장이 없다. 한 스레드 안에서 여러 요소의 처리가 **뒤섞여(interleaved)** 진행될 수 있다(SIMD 벡터화).
> 그래서 `par_unseq`에 넘기는 함수 안에서는 **뮤텍스를 잠그거나 메모리를 할당하면 안 된다.** 같은 스레드가 락을 두 번 잡아 데드락이 날 수 있다.
> 어떤 정책이든 공통 규칙은 하나다. **넘기는 함수는 부수 효과가 없어야 한다.**

### How it works

실행 정책 인터페이스는 알고리즘의 작업 부하가 **어떻게** 병렬화되는지 명시하지 않는다.
다양한 하드웨어와 프로세서에서 다양한 부하와 상황에 작동하도록 설계되었다.

병렬화는 **O(n)보다 큰 복잡도**를 가지는 알고리즘에서 가장 큰 향상을 보인다.

`sort()`를 기준으로 측정하면 이런 식이다.

| 정책 | 소요 시간 |
| --- | --- |
| 기본(순차) | 751 |
| `par` | 163 |
| `par_unseq` | 152 |

`sort()`는 O(n log n)이라 이득이 크지만, `transform`처럼 O(n)인 알고리즘은 **작업을 나누고 합치는 비용**이 이득을 깎아먹어 향상 폭이 작다.

> **실무 함정 하나.**
> GCC/libstdc++에서는 병렬 정책이 인텔 TBB에 의존한다. 라이브러리를 설치하고 `-ltbb`로 링크하지 않으면
> 컴파일은 되는데 조용히 **순차 실행으로 떨어지거나** 링크 에러가 난다. "정책을 넣었는데 왜 안 빨라지지?"의 대부분이 이 경우다.

## 뮤텍스와 잠금으로 데이터 안전하게 공유하기

**뮤텍스(mutex)** 는 **상호 배타적(mutual exclusion) 접근**을 의미한다.
여러 스레드가 동일한 데이터에 동시에 접근하려고 할 때 이를 막는 역할을 한다.

### How to do it

기본적으로는 이런 식으로 잠그고 푼다.

```cpp
animal_mutex.lock();
// 임계 구역
animal_mutex.unlock();
```

하지만 `lock()`, `unlock()` 메서드는 **직접 호출되는 일이 거의 없다.**
`std::lock_guard` 클래스는 자원 획득이 초기화(RAII) 패턴으로 잠금을 관리하며,
`lock_guard` 객체가 파괴될 때 **자동으로 잠금이 해제된다.**

```cpp
{
    std::lock_guard<std::mutex> lg{ animal_mutex };
    // 임계 구역
}   // 여기서 자동으로 unlock
```

> **왜 수동 `lock()`/`unlock()`이 위험한가?**
> 임계 구역 안에서 예외가 던져지거나 `return`이 끼면 `unlock()`이 실행되지 않는다. 그러면 그 뮤텍스는 **영원히 잠긴 채** 남고, 다른 스레드는 전부 멈춘다.
> RAII는 스택 되감기 과정에서 소멸자를 반드시 호출하므로 이 사고가 원천적으로 불가능하다.

잠금 클래스는 용도별로 나뉜다.

| 클래스 | 도입 | 특징 |
| --- | --- | --- |
| `lock_guard` | C++11 | 가장 단순. 생성 시 잠그고 소멸 시 푼다. 중간에 풀 수 없다 |
| `unique_lock` | C++11 | 중간에 `unlock()`/`lock()` 가능. **`condition_variable`은 이것을 요구한다** |
| `scoped_lock` | C++17 | **여러 뮤텍스를 데드락 없이** 한 번에 잠근다 |
| `shared_lock` | C++14 | `shared_mutex`용 읽기 잠금 |

여러 뮤텍스를 잡아야 할 때 `scoped_lock`이 중요하다.

```cpp
std::scoped_lock lock{ mtx_a, mtx_b };   // 순서에 관계없이 데드락 회피
```

두 스레드가 `a → b`, `b → a` 순으로 잠그면 서로를 기다리며 멈춘다(데드락).
`scoped_lock`은 내부적으로 데드락 회피 알고리즘을 써서 이 문제를 없앤다.

### How it works

여기서 반드시 이해해야 할 점이 있다.
**뮤텍스는 데이터를 잠그는 것이 아니라 실행을 중단한다.**

```cpp
mutex mtx;
int shared_value;   // mtx와 이 변수 사이에 언어적 연결은 없다
```

컴파일러는 `mtx`가 `shared_value`를 보호한다는 사실을 모른다.
누군가 락을 잡지 않고 `shared_value`에 접근해도 **아무도 막지 않는다.**
그 데이터에 접근하는 **모든 코드가 같은 뮤텍스를 잡는다는 약속**을 프로그래머가 지켜야 성립하는 규약이다.

또한 `mutex` 객체는 **어떤 스레드가 소유하고 있는 동안 파괴되어서는 안 된다.**
그래서 보통 전역이나, 보호 대상 데이터를 가진 클래스의 멤버로 둔다.

### There's more

`std::mutex`는 다양한 용도의 **독점적인** 뮤텍스를 제공하지만,
`shared_mutex`처럼 **여러 스레드가 동시에 소유할 수 있도록** 허용하는 뮤텍스도 있다.

```cpp
std::shared_mutex smtx;

void reader() {
    std::shared_lock lock{ smtx };   // 여러 독자가 동시에 진입 가능
    // 읽기만 한다
}

void writer() {
    std::unique_lock lock{ smtx };   // 작성자는 혼자만 진입
    // 쓴다
}
```

읽기가 압도적으로 많은 자료구조에서 효과가 크다.
독자끼리는 서로를 막지 않고, 작성자가 들어올 때만 전부 배제된다.

| 뮤텍스 | 용도 |
| --- | --- |
| `mutex` | 기본. 독점 잠금 |
| `timed_mutex` | `try_lock_for()`로 제한 시간을 두고 시도 |
| `recursive_mutex` | 같은 스레드가 여러 번 잠글 수 있음 |
| `shared_mutex` | 다수 독자 / 단일 작성자 |

## std::atomic으로 플래그와 값 공유하기

`std::atomic`은 할당 객체가 **원자적(atomic)** 임을 보장한다.
원자 객체에 대한 쓰기는 메모리 순서 정책에 의해 통제되며, 읽기는 동시에 발생할 수 있다.
타입은 **단순한(trivially copyable) 구조**여야 한다.

### How to do it

```cpp
std::atomic<bool> ready{};
std::atomic<uint64_t> g_count{};
std::atomic_flag winner{};

constexpr int max_count{ 1000 * 1000 };
constexpr int max_threads{ 100 };

string make_commas(const uint64_t& num) {
    string s{ std::to_string(num) };
    for (long l = s.length() - 3; l > 0; l -= 3) {
        s.insert(l, ",");
    }
    return s;
}

void countem(int id) {
    while (!ready) std::this_thread::yield();
    for (int i{}; i < max_count; ++i) ++g_count;
    if (!winner.test_and_set()) {
        std::cout << format("thread {:02} won!\n", id);
    }
}

int main() {
    vector<std::thread> swarm;
    cout << format("spawn {} threads\n", max_threads);
    for (int i{}; i < max_threads; ++i) {
        swarm.emplace_back(countem, i);
    }
    ready = true;
    for (auto& t : swarm) t.join();
    cout << format("global count: {}\n", make_commas(g_count));
    return 0;
}
```

100개의 스레드가 각각 100만 번씩 증가시키므로 결과는 정확히 **100,000,000**이 나온다.
`g_count`가 평범한 `uint64_t`였다면 `++`가 "읽기 → 더하기 → 쓰기" 세 단계로 쪼개지면서
증가분이 서로 덮어써져 **매번 다른, 항상 더 작은 값**이 나왔을 것이다.

코드의 세 부분을 각각 뜯어보면 이렇다.

```cpp
while (!ready) std::this_thread::yield();
```

모든 스레드를 **출발선에 세우는** 장치다. `main`이 `ready = true`를 할 때까지 대기하다가 동시에 출발한다.
`yield()`는 "내 시간 조각을 양보하겠다"는 힌트로, 바쁜 대기(busy wait)가 CPU를 덜 낭비하게 만든다.

```cpp
if (!winner.test_and_set()) { /* 1등 */ }
```

`test_and_set()`은 **플래그를 세우고 이전 값을 반환**한다. 이 두 동작이 원자적으로 일어나기 때문에,
100개 스레드가 동시에 호출해도 `false`를 받는 스레드는 **정확히 하나**다.

> `std::atomic_flag`는 **락 프리(lock-free)가 표준으로 보장되는 유일한 원자 타입**이다.
> 다른 `atomic<T>`는 타입이 크면 내부적으로 뮤텍스를 쓸 수도 있다. `x.is_lock_free()`로 확인할 수 있다.
> C++20부터는 `atomic_flag`도 `test()`로 값을 읽을 수 있고, 기본 초기화가 명확해졌다(그 전에는 `ATOMIC_FLAG_INIT`이 필요했다).

### How it works

`atomic` 클래스는 객체를 **캡슐화**한다. 캡슐화된 객체는 반드시 단순한 구조 타입이어야 한다.

```cpp
std::atomic<int>     a;   // OK
std::atomic<double*> p;   // OK
std::atomic<string>  s;   // 컴파일 에러 — trivially copyable이 아님
```

`string`처럼 내부에 힙 포인터가 있고 소멸자가 필요한 타입은 담을 수 없다.
"CPU 명령 하나로 통째로 읽고 쓸 수 있는 값"이어야 하기 때문이다.

`atomic`이 보장하는 것과 보장하지 않는 것을 구분해야 한다.

```cpp
std::atomic<int> x{};

++x;              // 원자적 — 안전
x = x + 1;        // 원자적이지 않다! 읽기와 쓰기가 별개의 연산이다
```

**하나의 연산**은 원자적이지만, **여러 연산을 조합**하면 그 사이에 다른 스레드가 끼어들 수 있다.
그런 경우에는 `compare_exchange_weak()`를 쓰거나, 결국 뮤텍스로 돌아가야 한다.

### There's more

여러 스레드가 동시에 변수를 읽고 쓰는 경우, 한 스레드는 변경 사항이 **쓰여진 순서와 다르게** 관찰될 수 있다.
컴파일러와 CPU 모두 성능을 위해 명령의 순서를 바꾸기 때문이다.

`std::memory_order`는 원자적 연산에 대해 메모리 접근 순서를 명시한다.

```cpp
g_count.fetch_add(1, std::memory_order_relaxed);   // 순서 보장 없이 카운트만
```

| 순서 | 의미 |
| --- | --- |
| `seq_cst` | **기본값.** 모든 스레드가 동일한 전역 순서를 관찰한다. 가장 안전하고 가장 느리다 |
| `acquire` / `release` | 한 쌍으로 써서 "이 지점 이전/이후"의 순서만 보장 |
| `relaxed` | 원자성만 보장, 순서는 보장 안 함. 단순 카운터에 적합 |

> 기본값 `seq_cst`가 있는 덕분에, 아무것도 지정하지 않아도 **직관대로 동작한다.**
> 메모리 순서를 손대는 건 프로파일링으로 병목이 확인된 뒤의 최적화이지, 처음부터 할 일이 아니다.

## std::call_once로 스레드 초기화하기

여러 스레드에서 **초기화를 단 한 번만** 해야 할 때 쓴다. `std::call_once`는 내부적으로 뮤텍스를 사용한다.

### How to do it

```cpp
using std::format;
using std::cout;
using std::list;
using std::thread;

constexpr size_t max_threads{ 25 };
std::once_flag init_flag;

void do_init(size_t id) {
    cout << format("do_init ({}): ", id);
}

void do_print(size_t id) {
    std::call_once(init_flag, do_init, id);
    cout << format("{} ", id);
}

int main() {
    list<thread> spawn;

    for (size_t id{}; id < max_threads; ++id) {
        spawn.emplace_back(do_print, id);
    }
    for (auto& t : spawn) t.join();
    cout << '\n';
}
```

25개 스레드가 모두 `call_once`를 호출하지만 `do_init`은 **딱 한 번만** 실행된다.
어느 스레드가 당첨될지는 실행할 때마다 다르므로, 출력되는 id도 매번 달라진다.

### How it works

`std::call_once`는 **플래그, callable, 그리고 인수의 파라미터 팩**을 받는 템플릿 함수다.

```cpp
template<typename Callable, typename... Args>
void call_once(std::once_flag& flag, Callable&& f, Args&&... args);
```

핵심은 단순히 "한 번만 실행"이 아니라, **먼저 도착한 스레드가 초기화를 끝낼 때까지 나머지가 기다린다**는 점이다.

```
스레드 A: call_once 진입 → do_init 실행 중 ..... 완료
스레드 B: call_once 진입 → (A가 끝날 때까지 대기) → 그냥 통과
```

만약 기다리지 않는다면, B는 아직 초기화가 덜 끝난 자원을 쓰게 된다. 이걸 막는 것이 `call_once`의 진짜 가치다.

> **호출된 함수가 예외를 던지면?**
> 플래그는 세워지지 않고, 다음 스레드가 다시 시도한다. 초기화가 실패한 채로 "완료됨"이 되는 사고를 막아준다.

한편 C++11 이후로는 **함수 지역 정적 변수의 초기화 자체가 스레드 안전**하다.

```cpp
Widget& instance() {
    static Widget w;   // 초기화는 한 번, 동시 접근 시 나머지는 대기한다
    return w;
}
```

싱글턴이 목적이라면 이쪽이 더 간단하다. `call_once`는 **초기화 대상이 정적 변수가 아닐 때** 유용하다.

## std::condition_variable을 사용하여 생산자-소비자 문제 해결하기

가장 단순한 버전의 생산자-소비자 문제는
**하나의 프로세스가 데이터를 생성하고, 다른 프로세스가 데이터를 소비하며, 데이터를 저장하기 위해 하나의 버퍼나 컨테이너를 사용하는 경우**다.

### How to do it

```cpp
using std::format;
using std::cout;
using std::mutex;
using std::thread;

using namespace std::chrono_literals;
namespace this_thread = std::this_thread;

using guard_t = std::lock_guard<std::mutex>;
using lock_t  = std::unique_lock<std::mutex>;

constexpr size_t num_items{ 10 };
constexpr auto delay_time{ 200ms };

std::deque<size_t> q{};
std::mutex mtx{};
std::condition_variable cond{};
bool finished{};

void producer() {
    for (size_t i{}; i < num_items; ++i) {
        this_thread::sleep_for(delay_time);
        guard_t x{ mtx };
        q.push_back(i);
        cond.notify_all();
    }

    guard_t x{ mtx };
    finished = true;
    cond.notify_all();
}

void consumer() {
    while (!finished) {
        lock_t lck{ mtx };
        cond.wait(lck, []{ return !q.empty() || finished; });
        while (!q.empty()) {
            cout << format("Got {} from the queue\n", q.front());
            q.pop_front();
        }
    }
}

int main() {
    thread t1{ producer };
    thread t2{ consumer };
    t1.join();
    t2.join();
    cout << "finished!\n";
}
```

생산자에서 데이터를 넣고, 소비자에서 `cond.wait`로 데이터를 기다렸다가 소비한다.

> **`condition_variable`이 없으면 어떻게 되는가?**
> 소비자는 큐가 빌 때마다 `while (q.empty()) {}`로 계속 확인해야 한다(폴링). CPU를 100% 태우면서 아무 일도 하지 않는다.
> `wait()`는 스레드를 **커널 수준에서 재우고**, `notify`가 올 때만 깨운다. 대기하는 동안 CPU를 전혀 쓰지 않는 게 핵심이다.

### How it works

`wait()`의 동작이 이 코드의 전부라고 해도 과언이 아니다.

```cpp
cond.wait(lck, []{ return !q.empty() || finished; });
```

내부적으로 이 한 줄은 세 가지를 원자적으로 처리한다.

1. 조건자(predicate)를 평가한다. **참이면 그대로 통과**한다(안 기다린다).
2. 거짓이면 **뮤텍스를 풀고** 잠든다. ← 이게 결정적이다. 잠긴 채로 자면 생산자가 큐에 넣을 수 없어 영원히 데드락이다.
3. 깨어나면 **뮤텍스를 다시 잡고** 1번으로 돌아간다.

3번의 "다시 확인"이 필요한 이유는 **가짜 기상(spurious wakeup)** 때문이다.
`condition_variable`은 아무도 알리지 않았는데 깨어날 수 있다. 그래서 조건자 없는 형태는 항상 이렇게 감싸야 한다.

```cpp
while (!조건) cond.wait(lck);          // 조건자 없는 형태는 반드시 while로
cond.wait(lck, []{ return 조건; });    // 위와 정확히 동일 — 이쪽을 쓰자
```

`wait()`가 `lock_guard`가 아니라 **`unique_lock`을 요구하는 이유**도 이제 분명하다.
중간에 뮤텍스를 풀었다 다시 잡아야 하는데, `lock_guard`에는 그런 기능이 없다.

깨우는 쪽은 두 가지 선택지가 있다.

| 함수 | 의미 |
| --- | --- |
| `notify_one()` | 대기 중인 스레드 **하나만** 깨운다 |
| `notify_all()` | 대기 중인 **모두** 깨운다 |

`condition_variable` 클래스는 `notify_one`과 `notify_all`로 대기 중인 스레드를 깨운다.

> **이 예제에는 실제로 데이터 경쟁이 있다.**
> `consumer`의 `while (!finished)`는 **뮤텍스를 잡지 않은 채** `finished`를 읽는다. 생산자는 잠금을 쥐고 쓰는데 말이다.
> 실전에서는 `std::atomic<bool> finished{};`로 바꾸는 것이 옳다. 예제를 단순하게 유지하느라 생략된 부분이니, 그대로 복사해 쓰지는 말자.

## 다수의 생산자와 소비자 구현하기

생산자-소비자 문제에서는 **버퍼가 유한한지 무한한지**, **생산자와 소비자가 하나인지 여럿인지**에 따라 해결 방법이 달라진다.

| 구분 | 필요한 것 |
| --- | --- |
| 무한 버퍼 | 소비자만 기다리면 된다 (`condition_variable` 1개) |
| **유한 버퍼** | 큐가 가득 차면 **생산자도 기다려야 한다** (`condition_variable` 2개) |

### How to do it

```cpp
using std::format;
using std::cout;
using std::string;
using std::list;
using std::mutex;
using std::unique_lock;
using std::async;
using std::future;
using std::condition_variable;

using namespace std::chrono_literals;
namespace this_thread = std::this_thread;

constexpr auto delay_time{ 50ms };
constexpr auto consumer_wait{ 100ms };
constexpr size_t queue_limit{ 5 };
constexpr size_t num_items{ 15 };
constexpr size_t num_producers{ 3 };
constexpr size_t num_consumers{ 5 };

std::deque<string> qs{};
mutex q_mutex{};
condition_variable cv_producer{};
condition_variable cv_consumer{};
bool production_complete{};

void producer(const size_t id) {
    for (size_t i{}; i < num_items; ++i) {
        this_thread::sleep_for(delay_time * id);
        unique_lock<mutex> lock(q_mutex);
        cv_producer.wait(lock, [&]{ return qs.size() < queue_limit; });
        qs.push_back(format("pid {}, qs  {}, item {:02}\n", id, qs.size(), i + 1));
        cv_consumer.notify_all();
    }
}

void consumer(const size_t id) {
    while (!production_complete) {
        unique_lock<mutex> lock(q_mutex);
        cv_consumer.wait_for(lock, consumer_wait, [&]{ return !qs.empty(); });
        if (!qs.empty()) {
            cout << format("cid {}: {}", id, qs.front());
            qs.pop_front();
        }
        cv_producer.notify_all();
    }
}

int main() {
    list<future<void>> producers;
    list<future<void>> consumers;

    for (size_t i{}; i < num_producers; ++i) {
        producers.emplace_back(async(producer, i));
    }

    for (size_t i{}; i < num_consumers; ++i) {
        consumers.emplace_back(async(consumer, i));
    }

    for (auto& f : producers) f.wait();
    production_complete = true;
    cout << "producers done.\n";

    for (auto& f : consumers) f.wait();
    cout << "consumers done.\n";
}
```

여러 생산자와 소비자가 있으며 **유한 버퍼**를 사용하는 경우다.
`producer(const size_t id)`의 `id`는 생산자를 식별하는 데 사용되는 일련번호다.
`main`에서 `async`를 사용하여 생산자와 소비자 스레드를 생성한다.

`sleep_for(delay_time * id)`로 생산자마다 다른 속도를 준 것이 포인트다.
빠른 생산자가 큐를 가득 채우면 `cv_producer.wait`에 걸려 스스로 멈추고, 소비자가 하나 빼내면 다시 깨어난다.

### How it works

핵심은 **두 개의 `condition_variable` 객체를 사용하여 producer와 consumer 스레드를 비동기로 제어**하는 것이다.

```
생산자: "큐에 자리가 생겼나?"  → cv_producer 에서 대기
소비자: "큐에 물건이 있나?"    → cv_consumer 에서 대기

생산자가 넣으면 → cv_consumer.notify_all()  (소비자를 깨움)
소비자가 빼면   → cv_producer.notify_all()  (생산자를 깨움)
```

**서로가 서로를 깨우는 구조**다. 각자 기다리는 조건이 다르기 때문에 조건 변수도 두 개여야 한다.

> **하나로 합치면 안 되는가?**
> 동작은 한다. 다만 `notify_all` 한 번에 생산자와 소비자가 **전부** 깨어나고, 대부분은 조건이 맞지 않아 그대로 다시 잠든다.
> 이 헛깨움을 **thundering herd**라고 부른다. 두 개로 나누면 필요한 쪽만 깨어난다.

소비자가 `wait`가 아니라 `wait_for`를 쓰는 것도 이유가 있다.

```cpp
cv_consumer.wait_for(lock, consumer_wait, [&]{ return !qs.empty(); });
```

생산이 모두 끝나면 아무도 `cv_consumer`를 깨우지 않는다.
`wait`였다면 소비자들이 영원히 잠들어 `f.wait()`가 돌아오지 않는다.
`wait_for`는 100ms 뒤 스스로 깨어나 `while (!production_complete)` 조건을 다시 확인하므로 종료할 수 있다.

> **이 예제에도 손볼 곳이 둘 있다.**
> 1. `production_complete`가 평범한 `bool`이다. 여러 스레드가 락 없이 읽고 `main`이 쓰므로 데이터 경쟁이다. `std::atomic<bool>`이 맞다.
> 2. `async(producer, i)`에 **실행 정책이 없다.** 구현이 `deferred`를 고르면 `f.wait()`를 부르기 전까지 생산자가 시작조차 하지 않아 프로그램이 멈춘다. `async(launch::async, producer, i)`로 명시해야 안전하다.
>
> 종료 신호를 타임아웃으로 처리하는 대신 **큐에 "종료" 표식(sentinel)을 넣는 방식**도 흔히 쓰인다. 소비자가 그 표식을 보면 빠져나오는 구조라 대기 시간이 낭비되지 않는다.

## 정리

이번 장에서 나온 도구들을 목적별로 정리하면 이렇다.

| 하고 싶은 일 | 도구 |
| --- | --- |
| 백그라운드에서 함수 실행 | `std::thread`, `std::jthread`(C++20) |
| 백그라운드 실행 + **결과 받기** | `std::async` + `std::future` |
| 표준 알고리즘을 여러 코어로 | `std::execution::par` |
| 공유 데이터 보호 | `std::mutex` + `lock_guard` / `scoped_lock` |
| 단일 값·플래그 공유 | `std::atomic` |
| 초기화 한 번만 | `std::call_once`, 함수 지역 `static` |
| 스레드끼리 신호 주고받기 | `std::condition_variable` |

선택 순서는 대체로 이렇다.
**결과가 필요하면 `async`, 수명 관리가 필요하면 `jthread`, 단순 카운터면 `atomic`, 그보다 복잡하면 `mutex`, 기다림이 필요하면 `condition_variable`.**
그리고 가능하다면 **공유 상태 자체를 만들지 않는 것**이 언제나 가장 좋은 해법이다.
